# 15. Production is Terraform in the repository, applied by CI, deployed on every merge

Date: 2026-10-18

## Status

Proposed. Amends `docs/build-plan.md` item 5.2: the API deploys on every merge to `main`
rather than behind a manual trigger, and the AWS resources are code rather than console
steps.

## Context

Build plan 5.2 fixes the shape of production: one EC2 host with nginx, PHP-FPM, and the
queue worker (ADR 0007), Postgres on RDS, the PWA on S3 behind CloudFront, and GitHub
Actions signing in to AWS through OIDC. It does not say how those resources come to exist.
Made by hand in the console, they could not be reviewed, rebuilt, or read at the
examination, and every later change would be a click no one else can see.

The deadline also matters: production is wanted by 21 October, by two developers, one of
whom applies and the other reviews.

## Decision

1. **Terraform, in `infra/`.** Every AWS resource is declared there and changed through a
   merge request like any other code. Terraform rather than CloudFormation or the CDK: its
   plan shows exactly what a change creates, changes, or destroys before anything happens,
   and that plan is what a reviewer reads.
2. **Two stacks.** `infra/bootstrap` holds what production's Terraform cannot make for
   itself: the bucket its state lives in, GitHub's OIDC sign-in, and two roles. It is
   applied once, from a developer's machine with their own sign-in, and its state stays on
   that machine. `infra/production` holds everything else; its state is in the bucket, with
   Terraform's own lock file there (`use_lockfile`), so no lock table.
3. **CI plans and applies; no developer applies production after the first time.** A merge
   request touching `infra/production` gets a plan from the read-only **plan** role, posted
   as a comment. A merge to `main` applies it with the **apply** role. Neither role can be
   taken by anything but a workflow of this repository: the plan role only for a merge
   request, the apply role only for a run on `main`. The apply role is an administrator,
   because Terraform creates roles itself; what guards it is who can assume it, and only a
   reviewed merge reaches `main`.
4. **Every merge to `main` deploys** (amending 5.2's manual trigger). Two things carry the
   safety a manual trigger gave. Migrations stay additive only (a standing constraint), so a
   deploy never breaks a device that has not yet synced; and each deploy is a new release
   directory that goes live only when install, migrations, and caching have all succeeded,
   so a failed deploy leaves the previous release serving. A canary can be added later
   without restructuring.
5. **No secret in the repository or in GitHub.** GitHub holds role names, not keys. The
   database password is created and rotated by RDS in Secrets Manager and never passes
   through Terraform. The application's settings are in Parameter Store under
   `/connected/production/`, from which each deploy writes the host's `.env`. Laravel's key
   and CloudFront's origin secret are generated by Terraform and so are also in its state,
   which is why that bucket is private, encrypted, and versioned.
6. **Small and single-zone.** The default network with security groups doing the
   isolation, not private subnets behind a NAT gateway; a `t4g.small` host; a `db.t4g.micro`
   database in one availability zone with seven days of backups; a monthly budget alarm.
   About $35 to $50 a month in Cape Town (`af-south-1`), the closest region to Kenya.
7. **One HTTPS address for everything, before there is a domain.** CloudFront's own
   address serves the PWA from S3 and sends `/api`, `/admin`, and the panel's assets to the
   host, uncached, so the service worker's same-origin `/api` holds (5.2's review, item 8).
   CloudFront reaches the host over plain HTTP, since a certificate needs a domain; the host
   accepts traffic only from CloudFront's published address range, and nginx also refuses
   any request without a secret header CloudFront adds. A domain, when there is one, moves
   that leg to HTTPS as a Terraform change.

## Considered and rejected

- **The console, with a written runbook.** Quicker to start, but nothing to review or
  rebuild, and nothing to show at the examination.
- **A manual deploy trigger, or an approval gate on each merge.** The gate protects
  migrations, which the additive-only rule already protects, at the cost of a step someone
  must remember.
- **Long-lived AWS keys in GitHub secrets.** One leaked key would be the whole account.
- **Private subnets with a NAT gateway, Multi-AZ RDS, a load balancer.** Each is a real
  production practice and each costs more per month than everything else here, for
  availability a pilot does not need.
- **Laravel Cloud or Forge.** ADR 0000 and the build plan name AWS, and a managed platform
  would hide the deployment the project needs to be able to explain.

## Consequences

- Production can be rebuilt from the repository, in a fresh account, by applying the two
  stacks.
- A merge that touches `infra/production` changes real resources minutes later; its plan
  comment is the review.
- The bootstrap's local state is the one piece outside the repository. Losing it costs
  nothing running; its resources can be imported into a fresh state.
- The AWS account moved to the paid plan when IAM Identity Center was enabled through AWS
  Organizations, so the costs above are real from the first apply. The budget alarm is
  part of the code for that reason.
