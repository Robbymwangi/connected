# 4. Offline install with Workbox

Date: 2026-09-17
Superseded a hand-written worker on the same day, before either shipped.

## Status

Accepted. (This decision reverses the first version of this ADR, which chose a
hand-written worker; that reasoning is kept below under "What was tried first".)

## Context

The application must open and work with no connectivity, which is its normal resting
state, and it auto-updates: a new build changes every asset's content hash. The hard
part is not the first offline load; it is staying correct across an update, when a
newly built worker is installed but waiting behind the one still in control. In that
window the cached shell and the cached assets can come from different builds, and an
offline reload then fails to fetch a hashed bundle. This is the precise failure that
appeared in testing.

## Decision

The worker is generated by Workbox through `vite-plugin-pwa`, configured in
`frontend/vite.config.ts`:

- `generateSW` precaches every built asset (`**/*.{js,css,html,woff2,svg,png,webmanifest}`)
  with a content-hashed manifest, versions the cache, and cleans up old versions
  (`cleanupOutdatedCaches`). This is the part that must be exactly right across
  updates, and is what Workbox exists to do.
- `navigateFallback: '/index.html'` serves the app shell for navigations;
  `navigateFallbackDenylist: [/^\/api\//]` keeps API paths off it.
- `registerType: 'prompt'` with `skipWaiting` left off: a new version waits until the
  user reloads, so the app never swaps mid-marking. `clientsClaim: true` lets the
  worker control the page on the first visit, so offline works without a second load.
- `devOptions.enabled: false`: no worker in development, so the dev server's live
  reload is not fought.

Registration and the update prompt are in `frontend/src/lib/serviceWorker.ts` via
`virtual:pwa-register`; the shell's `UpdateReady` bar calls the update function.

## What was tried first, and why it was dropped

The worker was first written by hand (about eighty lines) with a Vite plugin that
wrote the precache list, to keep every line explainable and avoid a runtime
dependency. It served a clean first install correctly, but did not reliably survive
the update transition: across a new build, an offline reload could be answered with a
shell whose hashed assets were not in the controlling worker's cache, and the page
failed to load. Several attempts to fix it by hand (scoping cache lookups to the
active version among them) did not close the gap, and the failure was hard to
reproduce and observe. For a guarantee this load-bearing, a from-scratch worker was
the wrong economy; Workbox solves exactly this and is proven across many PWAs.

## Consequences

- A Workbox runtime is added to the bundle (about 6 KiB gzipped for the registration
  helper, plus the generated worker). Acceptable for the offline guarantee.
- The offline behaviour across first install, update, and reload is verified by a
  test rather than asserted (see the PWA end-to-end test).
- The team defends "we precache with Workbox's generateSW because the update
  lifecycle is subtle" rather than a bespoke worker; that is a sound decision to
  defend at a viva.
- A web app manifest and icons (`public/`) make the app installable.
